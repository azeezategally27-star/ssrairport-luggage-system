How it works — tiny

  1. Compute pressures p_i by solving linear system (Kirchhoff) for node potentials with sources/sinks.
  2. Flux Q_ij = D_ij * (p_i - p_j) / L_ij.
  3. D_ij ← D_ij + dt*(α*|Q_ij| - β*D_ij) — edges with flow strengthen, others decay.

C backend (core) — server, solver, scan ingest

Keep the heavy computation and all sensitive integrations in a compiled, performant C process. This example aligns with the code in your repo (msgbus, agents, backend_server). The backend exposes a TCP or Unix socket API for frontends to query solver state, push scans, and subscribe to events.

Backend roles

  • Real‑time Physarum solver (updates conductances) — numeric stability & performance in C.
  • Scan ingestion: receive X‑ray frames or meta streams, run fast scoring or call an ONNX runtime extractor.
  • Event bus: publish events (GATE_ASSIGNED, ALERT, BAG_ROUTED) over message queue and socket endpoints.
  • Security: run with least privilege, sanitize inputs, log high‑level metadata only (apply legal rules).

Key C snippet: solver update (concept)

// physarum_step.c (conceptual)
#include <math.h>
void physarum_step(edge_t *edges, int E, double dt, double alpha, double beta){
  // edges contain D, L, endpoints a,b; pressures p[] computed separately.
  for(int i=0;i<E;++i){
    double Q = edges[i].D * (p[edges[i].a] - p[edges[i].b]) / edges[i].L;
    edges[i].D += dt * (alpha * fabs(Q) - beta * edges[i].D);
    if(edges[i].D < 1e-6) edges[i].D = 1e-6;
  }
}

The C backend periodically solves pressure equations and updates D. It stores graph state in memory and persists checkpoints (optional SQLite for persistence).

Frontends — multiple languages (why & how)

Frontends are UI-focused: 3D previews, operator dashboards, and quick terminal tools. They connect to the C backend over TCP/UNIX socket or via message-bus bridge.

JavaScript (Three.js) — 3D visualization

A WebGL frontend shows flowing tubes (thickness = conductance) and per-bag anomaly overlays. The web client periodically polls the C backend for conductances and bag scores, and animates accordingly.

Python desktop (moderngl / PyOpenGL)

Terminal UI (ncurses)

For kiosks or remote terminals, an ncurses frontend (C or Python) shows logs, alerts, and simple enroll/verify keys. Quick and reliable.

X‑Ray Security pipeline — high level & safety

We architect the security pipeline so that the C backend processes sensitive frames and returns high‑level, auditable scores; frontends only receive non-sensitive metadata and visual cues. Human‑in‑the‑loop review is enforced before any enforcement action.

Pipeline steps

  1. Frame ingest (C): read frame, pre-process, optionally run optimized ONNX extractor.
  2. Scoring (C): compute anomaly score. If score>threshold → publish ALERT event (no raw image in event).
  3. Operator review (frontend): show composite visualization; on confirm → record audit log and escalate.

Sample server command exchange (text protocol)

// client <-> C backend (TCP simple protocol)
// ENROLL <id>
// VERIFY <id>
// INGEST_SCAN <bagid> <binary-frame>  (binary stream framed)
// QUERY_STATE
// ALERT <bagid> <score>

PRIVACY: do not transmit raw frames to cloud or store them long term. Store only derived features and event logs unless a clear lawful requirement exists.

Optimization: reduce bottlenecks at peak

Combine predictive scheduling (flight manifests), Physarum routing, and adaptive lane scaling. The C backend uses scheduled events + live telemetry to bias source strengths in the solver (S_i), making the network pre-adapt before peaks.

Pseudocode: peak handling

// when future flight list predicts load
for each upcoming flight f at time T:
  schedule source boost: S[node(f)] += expected_pax(f)/scale
// solver then strengthens links ahead of time

This reduces sudden reroutes and mechanical re‑loads by adapting network geometry proactively.
